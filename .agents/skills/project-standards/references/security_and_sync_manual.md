# Security & Synchronization Manual

This manual describes the mechanisms designed to ensure player data integrity, prevent cheating, and manage real-time concurrency.

---

## 🔑 Security Context

### Online vs Offline Isolation

* **Online Mode**: Relies on **Row Level Security (RLS)** and server-side JWT verification. The client is untrusted; the server enforces boundaries.
* **Offline Mode**: Relies on **Client Isolation**. Since the database is local to the user's browser, the user is the de-facto admin of their own SQLite instance. "Security through Locality" ensures that a local user cannot affect global state or other players.

## 🛡️ Anti-Cheat & Sanitization Logic

The security system is based on continuous validation of the game state before every persistence event.

### 1. Data Integrity

Every save attempt passes through a technical filter. For gameplay-specific rules (e.g., non-negative money, UID uniqueness), see [game_rules_manual.md](./game_rules_manual.md).

### 2. Security Versions (v1 vs v2)

* **v1 Accounts (Legacy)**: Receive "silent" sanitization. The system cleans the data and saves it. Upon the first successful save, the account is automatically migrated to v2.
* **v2+ Accounts (Strict)**: If a critical inconsistency is detected (such as duplicate UIDs), the system triggers the **Rollback Protocol** instead of attempting to sanitize and save potentially corrupt data.

### 3. Combat Shielding (Stat Freezing)

To avoid cache manipulation during a fight (e.g., hacking money via console):

* **Battle Snapshot**: Upon starting a fight (`START_BATTLE`), the system takes a snapshot of money, XP, and critical items.
* **Delta Validation**: Upon finishing, the system only accepts the increment generated by the battle engine. If the values exceed logical sanity limits, the save is rejected.

### 4. Time-Sync Validator (Weather & Epoch Checks)

To prevent players from manipulating their local device clock to encounter time-specific or weather-specific Pokémon (Time Travel exploit), all saves uploaded to Supabase will be audited by an **Edge Function**.

* **Authoritative Time (Epoch Hours)**: Authoritative time is calculated as `Floor(ServerTime / 3,600,000)`, representing a unique, continuous identifier for each hour of real-world time.
* **Anti-Past (No Retroactive Time-Travel)**: A Pokémon's `caughtAt` timestamp cannot be older than the account's `last_sync_time`.
* **Anti-Future**: A Pokémon's `caughtAt` cannot exceed the authoritative Server Time.
* **Deterministic Weather Audit**: The Edge Function executes the exact same PRNG seed math used by the client.
  * **Seed Calculation**: `(HashString(RouteID) + EpochHour) >>> 0`.
  * **PRNG Engine**: Mulberry32.
  * **Avalanche Protocol**: To ensure high entropy when seeds differ by small amounts (e.g., sequential hours), the PRNG **MUST** discard the first 3 generated values before using the result.
  * **Validation**: If the weather recorded on the caught Pokémon does not mathematically match the weather that actually existed at that hour/route, the save is rejected.
* **Legacy Save Exception**: Saves migrating from older versions (e.g., v0 or v1) MUST bypass this validation for their pre-existing Pokémon.

## 🔄 Rollback System

There are two types of Rollback designed to protect the user's save file:

### 1. Local Inconsistency Rollback

If the engine detects that the current state in memory is invalid (e.g., duplicate UIDs in a v2 account), the save is canceled, and the game downloads the last known valid copy from the Cloud server.

### 2. Concurrency Rollback (`OUT_OF_SYNC`)

To prevent an old tab from overwriting progress from a new tab, the system uses an **Expected ID**:

* Each save generates a unique ID on the server.
* When attempting to save, the client sends the ID it believes is current (`p_expected_id`).
* If the server has a different ID, it means the user saved from another device or tab. The server rejects the operation, and the client performs a rollback to the server's version.

### 3. Post-Combat Synchronization (Delta Merge)

If you receive an external update (such as an accepted trade) while in battle:

* **Deferred Synchronization**: The system queues external changes to avoid corrupting the active fight.
* **Result Merge**: After the battle, if a de-sync conflict occurs, the client downloads the new "truth" from the server and applies the results (EXP, Gold) earned in the local combat (**Delta Merge**).

## ⏱️ Cache & Throttling (60-Second Sync)

To minimize server load and optimize performance on mobile devices, the project applies the **60-Second Synchronization Principle**.

* **Resource Savings**: Minor changes are not sent instantly to the cloud. They accumulate in a local cache that syncs periodically.
* **Critical Events**: Certain actions (winning a badge, catching a legendary, performing a trade) force an immediate save, ignoring the 60-second interval.
* **Cache Invalidation**: Upon login or opening a new tab, the system **MUST** invalidate any local cache and force a complete cloud download.
  * **Technical Action**: Ensure `authStore` initializes with `loading: true` and fetches the latest "Source of Truth" from the DBRouter.
* **Pre-Action Flush Protocol**: Before any social action other than chat (sending a trade, GTS listing, etc.), the system triggers a forced atomic save to ensure synchronization integrity.
* **Mandatory Claim Sync**: When using the "Receive All" function or claiming an individual asset, the system forces a prior save to prevent the local state from overwriting the incoming data.
* **Identity Synchronization Protocol**: To ensure visual parity across sessions, the application MUST synchronize the account-level identity (`auth.users`) with the game-level profile.
  * **Fallback Logic**: If `game.trainer` is missing or default, UI layers MUST display the `username` from the authentication metadata.
  * **Store Isolation**: Use a dedicated `profileStore` to manage identity metadata, breaking potential circular dependencies between the core UI and Game stores.

## 📡 Websockets & Realtime

The project uses **Supabase Realtime** (Websockets) to keep the world and session states synced without needing a page reload.

### 1. Single Session Lock (`session_lock`)

The DBRouter subscribes to a specific channel for the user. If a database change made by another instance (another tab) is detected, the channel emits an event that:

* Displays a locking overlay.
* Automatically closes the local DBRouter's write permissions.

### 2. Social Systems & PvP

The Realtime system is the engine behind:

* **Global Chat**: Distributed instant messaging.
* **GTS (Global Trade System)**: Real-time updates for item and Pokémon listings and sales.
* **Live PvP**: Invitation management and battle states through event broadcasting.

## 💎 Asset Management & Abuse Control

Server-centric architecture to ensure the integrity of Pokémon and items and prevent transaction spam.

### 1. Asset Escrow & Claims

Trading and sales follow a server-side escrow model. Refer to [game_rules_manual.md](./game_rules_manual.md) for rules regarding atomic claiming and claim queues.

### 2. Anti-Spam & Quotas

To prevent server overload, the system enforces cooldowns and capacity limits. See the [game_rules_manual.md](./game_rules_manual.md) for the specific cooldown and quota values.

### 3. Orphan Record Cleanup

To keep the database optimized and prevent stale data accumulation:

* **Automatic Deletion**: If both players involved in a trade (sender and recipient) cease to exist or their accounts are deleted, the system must automatically purge those records.
* **Referential Integrity**: Priority is given to foreign keys with cascade deletion (`ON DELETE CASCADE`) or scheduled maintenance processes to clean up offers that can no longer be claimed by either party.

## 🛠️ Debug & Administrative Security

### 1. Debug Panel Access Control

The **Local Debug Panel** (`LocalDebugPanel.vue`) is a sensitive administrative tool. Its visibility and instantiation are governed by strict security rules:

* **Offline Mandate**: In `offline` mode, the user is the local environment's administrator. Access is granted by default.
* **Online Restriction**: In `online` mode, access is strictly limited to accounts with the `admin` role.
* **Conditional Rendering**: The panel **MUST NOT** be rendered in the DOM (`v-if`) if the access check fails. This prevents accidental exposure of debug triggers to standard players.
* **CLI Proxy Security**: Every command exposed via `window.__VITE_DEBUG__` is protected by a centralized `securityCheck()`.
* **Auto-Ban Protocol**: Any unauthorized call to an administrative CLI command in an `online` session triggers an immediate record update in the `profiles` table (`is_banned: true`) followed by a forced `auth.logout()`.
* **Layering & Z-Index**: All administrative tools MUST respect the centralized z-index scale. Consult [ui_ux_standards.md](./ui_ux_standards.md) for layering and "Critical Layer" (999,999) protocols.
* **Emergency Utility Set**: The debug system includes a standard set of "Emergency" commands for rapid recovery:
  * `factoryResetLocal()`: Performs a total purge of local browser storage and session data.
  * `forceSyncCloud()`: Bypasses standard synchronization throttles to force an immediate state push to the cloud.
  * `setTimeOffset(ms)`: Allows administrative time-travel for testing time-dependent events. In `online` mode, this only affects the local client session and does NOT modify the remote server's actual clock or persistence.
  * `time-sync-update`: Administrative time changes MUST dispatch this CustomEvent to notify all reactive stores (`mapStore`, `gameStore`) to recalculate cycles, seasons, and deterministic weather.
